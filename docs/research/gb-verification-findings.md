# Game Boy implementation: verification and testing findings

This is a running log of what the fork's verification tooling has found in MesenCE's Game Boy
core (`Core/Gameboy`): bugs, deliberate divergences, and checks that came back clean. The method
mirrors the NES work in [nes-verification-findings.md](nes-verification-findings.md).

Snapshot: `master` @ `9a05146d`, 2026-11-04, aarch64-darwin.

## Summary

| # | Area | Finding | Status |
|---|---|---|---|
| 1 | SM83 CPU | 498/500 opcodes (incl. all 256 CB-prefixed) match SingleStepTests on **bus trace, final registers, RAM and M-cycle count** across 500,000 tests | **Clean** |
| 2 | CPU: `STOP` (`$10`) | MesenCE treats STOP as 2 bytes (reads and skips the next byte) | **Divergence.** Matches Pan Docs' normal case |
| 3 | CPU: `HALT` (`$76`) | Final state matches; M-cycle count differs (1 vs 3) | **Bookkeeping difference**, not a bug |
| 4 | Save states | 261 MesenTests GB/GBC ROMs × 300 frames (ROM-only, MBC1, MBC2, MBC3 incl. RTC, MBC5) reproduce exactly in a fresh console | **Clean** |
| 5 | Undefined behaviour | UBSan over MesenTests (earlier NES run), the CPU suite and the save-state round-trip | see §5 |

## How to reproduce

| Task | What it runs |
|---|---|
| `mise run test:gb-cpu` | `tools/gb-cpu-singlestep`. Clones [SingleStepTests/sm83](https://github.com/SingleStepTests/sm83) (about 150 MB) into `bin/` and runs all 500 × 1,000 tests. Exits non-zero only on *unexpected* failures |
| `mise run test:savestate -- <roms or dir>` | `tools/savestate-roundtrip`. `.gb`/`.gbc` files use the `Gameboy` console, `.nes` files `NesConsole` |

The ROMs for finding 4 are the `TestRom.*` files inside MesenTests' `GB/**/*.mtp` archives: 261
unique ROMs (256 `.gb`, 5 `.gbc`), mostly blargg, mooneye and the GBEmulatorShootout suites. By
cartridge type (header byte `$147`): 174 ROM-only, 65 MBC1 (`$01-$03`), 7 MBC2 (`$05-$06`), 5
MBC3+RTC (`$0F`, `$10`), 1 MBC3+RAM+battery (`$13`), and 9 MBC5 (`$19`, `$1B`). 83 of them have a
CGB-capable header.

## 1–3. SM83 CPU vs SingleStepTests `sm83`

**Method.** `tools/gb-cpu-singlestep/singlestep.cpp` runs every test twice from the same initial
state, on a real `Gameboy` console:

1. **`DummyGbCpu`** is the `GbCpu` source compiled with `DUMMYCPU`, which the debugger uses. It
   reads through `GbMemoryManager::DebugRead`, which the harness points at flat RAM: all 256 read
   pages map to one 64 KiB buffer, and every I/O-register page is disabled. Its logged
   reads/writes must equal the suite's `r-m`/`-wm` cycles in order (address, value, direction).
2. **The real `GbCpu`** runs on the same flat pages, with IE/IF cleared so no interrupt can be
   taken. It gives the final registers, IME, the EI-pending flag (`ei` in the suite), and final
   RAM. Writes go straight to the flat RAM, so there is no read-after-write limitation.
   **Timing** comes from `CycleCount`, which `GbMemoryManager::Exec` advances by 2, twice per
   M-cycle. Its delta divided by 4 must equal the number of cycle entries, including the idle
   (`---`) ones.

**Notes on the suite.**
- The expected values are generated by an emulator, not captured from hardware.
- The initial `ie` field is the IE register, not "EI pending": in the EI tests,
  `ie=1, ime=0` still ends with `ime=0`. The harness ignores it and starts with `EiPending=false`.
- Opcodes `$D3 $DB $DD $E3 $E4 $EB $EC $ED $F4 $FC $FD` (illegal on the SM83) have no tests.

**Result.** 498,000 of 500,000 pass, with 0 unexpected failures. All 256 CB-prefixed opcodes,
DAA, the 16-bit stack-pointer arithmetic (`ADD SP,e8` / `LD HL,SP+e8`), RETI, EI and DI match
exactly, timing included.

### 2. `STOP` (`$10`): 2-byte form (divergence)

- **What differs.** The suite expects PC+1 and 3 M-cycles, with one read. MesenCE reads the next
  byte as an ignored operand: 2 M-cycles, PC+2.
- **MesenCE** (`GbCpu.cpp:880-901`): `ReadCode()`, then a CGB speed switch or
  `Stopped`/`HaltCounter`. A `TODOGB` there notes that some STOP quirks aren't implemented.
- **Pan Docs** ([Reducing Power Consumption](https://gbdev.io/pandocs/Reducing_Power_Consumption.html)):
  STOP "is normally a 2-byte instruction where the second byte is ignored". Depending on
  conditions, it can instead act as STOP, HALT or a NOP, perform a speed switch, or become a
  1-byte opcode.
- **Conclusion.** MesenCE implements the documented normal case. The suite models one of the
  conditional variants. Not a bug. A full implementation of the Pan Docs flowchart (button state,
  pending interrupts, speed-switch request) would still be an accuracy improvement.

### 3. `HALT` (`$76`): cycle accounting (bookkeeping)

- **What differs.** All registers and RAM match. The suite lists 3 M-cycles (the fetch plus two
  idle); MesenCE's `Exec()` for HALT consumes 1. The halted time is then accounted on following
  `Exec()` calls (`HaltCounter`, `GbCpu.cpp:903-916`, `ProcessNextCycleStart`).
- **Conclusion.** Pan Docs gives no cycle count for HALT entry. Halt-exit timing is covered by the
  mooneye/blargg ROMs in MesenTests, which pass. Not a bug.

## 4. Save-state round trip

**Method.** As in the NES log:
1. Console A runs 120 frames, saves a state, then runs 300 more frames, recording its state after
   each one.
2. A **fresh** `Gameboy` console loads the ROM and the state, runs the same 300 frames, and is
   compared field by field after every frame.

**Result.** All 261 ROMs are consistent. Nothing emulation-relevant is missing from Game Boy save
states for these cartridge types. That includes MBC3 RTC carts, whose clock is derived from the
emulated master clock (`GbMbc3Rtc.h:75-86`) and is restored correctly.

**Harness note.** The first run crashed on the five RTC ROMs. `GbMbc3Rtc` reads time through
`Emulator::GetMasterClock()`, which forwards to the emulator's *current* console, and the harness
hadn't registered one. The harness now does what `Emulator::InitConsole` does
(`emu._console.reset(console)`). This was a harness defect, not an emulator bug.

## 5. Undefined behaviour

- **MesenTests** (all systems) under UBSan, from the NES session: no Game Boy reports. The only
  reports were the NES PPU bug and the WonderSwan palette indexes (see the NES log).
- **CPU suite and save-state round-trip under UBSan:** no reports. Both harnesses were linked
  against a `-fsanitize=undefined -fsanitize-recover=undefined` (`-O1 -g`) core and gave identical
  results: 498,000 / 500,000 with 0 unexpected failures, and 261 / 261 consistent.
- AddressSanitizer still can't run on this machine (see the NES log, §10).

## Ideas for further Game Boy verification

- **Interrupts and timing.** The per-instruction suite never takes an interrupt (IE=IF=0). Halt
  exit, the HALT bug, and IRQ dispatch timing are covered only by the mooneye/blargg ROMs in
  MesenTests. A TLA+ or exhaustive model of `GbCpu::Exec`'s IRQ/HALT/EI state machine
  (`_prevIrqVector`, `HaltCounter`, `HaltBug`, `EiPending`) would cover them, like the NES DMA
  model.
- **The full STOP behaviour** from the Pan Docs flowchart, as a test ROM plus implementation.
- **AddressSanitizer on Linux**, and a ThreadSanitizer run, since the Game Boy shares the
  audio/emulation-thread code with the NES.
