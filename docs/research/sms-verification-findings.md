# SMS / Game Gear / ColecoVision: verification and testing findings

This is a running log of what the fork's verification tooling has found in MesenCE's
SMS-family core (`Core/SMS`), whose CPU is a Z80 (`SmsCpu`). The method mirrors the NES and Game
Boy work in [nes-verification-findings.md](nes-verification-findings.md) and
[gb-verification-findings.md](gb-verification-findings.md). So far it covers the Z80 only.

Snapshot: `apply-verified-fixes` @ `c8ce0381`, 2026-11-05, aarch64-darwin.

## 1. Z80 vs SingleStepTests `z80`

**Method.** `tools/z80-cpu-singlestep/singlestep.cpp` compiles the **real** `Core/SMS/SmsCpu.cpp`
(without `DUMMYCPU`) into the harness as `TestSmsCpu`, with `SmsMemoryManager` replaced by a
`TestBus`: flat 64 KiB RAM, plus port reads served from the test's `ports` list. The code under
test is therefore the shipping instruction code; only the memory manager behind it differs.
`DummySmsCpu` compiles the same source, so the debugger gets the fixes too.

- **Bus trace:** memory and I/O accesses in order (address, value, direction). An access is a
  T-state with RD or WR together with MREQ or IORQ. Read data is taken from the following
  T-state, write data from the same one. `SmsCpu` passes 8-bit port numbers, so I/O addresses
  compare the low byte only (the SMS decodes 8 bits).
- **Timing:** the `SmsCpuState::CycleCount` delta must equal the number of T-state entries.
- **Final state:** all registers including IX/IY, the shadow set, I, R, **WZ** (MEMPTR), IM,
  IFF1/2, and **Q**. `SmsCpu` tracks Q as the `FlagsChanged` shift register; the suite's q is
  F when the previous instruction changed the flags and 0 otherwise, which maps onto bit 0. Plus
  final RAM.
- **Not checked:** the suite's `p` and `ei` fields. They only matter when an interrupt is
  accepted, and a single test instruction never takes one.

**Notes on the suite.**
- It is generated by an emulator (a translation of ares' Z80 core, plus bug fixes), not captured
  from hardware. It models an **NMOS** Z80. The Game Gear's Z80 is a CMOS part, which differs on
  `OUT (C),0` (it outputs `$FF`); MesenCE outputs 0 for all models.

### 2. Instruction timing (fixed)

Reference: Zilog *Z80 CPU User Manual* (UM0080), the per-instruction "T States" lines.

| Instruction | Zilog | MesenCE before | Cause |
|---|---|---|---|
| `INC (HL)` / `DEC (HL)` (`$34/$35`) | 11 (4,4,3) | 10 | No internal cycle between the read and the write |
| `INC/DEC (IX+d)` (`DD/FD 34/35`) | 23 | 22 | Same |
| `LD (HL),n` (`$36`) | 10 (4,3,3) | 12 | `LD_IndirectImm` always added the 2 cycles that only the indexed form has |
| `LD (IX+d),n` (`DD/FD 36`) | 19 (4,4,3,5,3) | 24 | The 5-cycle address calculation *and* the 2 extra cycles were both added. On the Z80 the address calculation overlaps with the fetch of n |
| `RLD` (`ED 6F`) | 18 (4,4,3,4,3) | 14 | The 4 internal cycles (present in `RRD`) were missing |
| `BIT b,(IX+d)` register aliases | 20 | 19 | Finding 3 |

**Effect.** CPU timing relative to the VDP and PSG. `LD (HL),n` and `INC/DEC (HL)` are common
instructions. MesenTests has no SMS tests (finding 9), so no system-level regression test covers
these changes.

### 3. `DD/FD CB d xx` BIT register aliases (fixed)

For the indexed CB page, every `BIT b` encoding (`$40-$7F`) reads `(IX+d)`, behaving like the
documented `BIT b,(IX+d)` (`$46`, `$4E`, ...). That includes 20 T-states and X/Y from the high
byte of WZ = IX+d. MesenCE routed the register forms through `BIT(reg)`. It read `(IX+d)`
(through `GetCbValue`) but took X/Y from the value and skipped the extra cycle. **Fix:**
`BIT()` hands off to `BIT_Indirect()` when `_cbAddress >= 0`. This replaces the branch
`GetCbValue` already made, so there's no extra work.

### 4. WZ / MEMPTR (fixed)

WZ is only observable through the X/Y flags of `BIT b,(HL)`. Rules from "memptr_eng.txt"
(boo_boo & Vladimir Kladov), which ares and the suite both follow:

- `JR e`: WZ = destination (conditional `JR` already did this).
- `JP nn`: WZ = nn (conditional `JP` already did this). `JP (HL)` shares `JP()` and must **not**
  set it, so the assignment is at the `$C3` call site.
- `LD SP,(nn)`: WZ = nn+1 (the `Register16` overload already did this; the `uint16_t&` overload
  didn't).
- Every `(IX+d)`/`(IY+d)` operand: WZ = IX+d. This now happens in `getIndirectHl`.

### 5. Block I/O flags (fixed)

Reference: Sean Young, *The Undocumented Z80 Documented* §4.3, and ares (`instructionINI` etc.).
Let `k = value + ((C ± 1) & 255)` for INI/IND, or `k = value + L` (L after the HL update) for
OUTI/OUTD:

- S, Z, X, Y from B (after the decrement). MesenCE did this already.
- **N = bit 7 of the value**. MesenCE always set N.
- **H = C = (k > 255)**. MesenCE left them unchanged.
- **P = parity((k & 7) xor B)**. MesenCE left it unchanged.

The repeat forms then apply the 2018 hardware findings (David Banks): X/Y from PC bits 11/13, and
P/H adjusted depending on C and N. MesenCE's `UpdateInOutRepeatFlags` already had this logic, but
tested **S** where the rule tests **N**. It also didn't set WZ = PC+1. `LDIR` and friends already
did.

**Judgment call.** Zilog's manual lists C as "not affected" by these instructions and N as
"set". Real silicon behaves as above, and the fork follows hardware.

### 6. `LD A,I` / `LD A,R` flag X (fixed)

`SetStandardFlags<0xE4>` updated S, Z, Y and P but not X (bit 3). The mask is now `0xEC`.

### 7. Q after `DD`/`FD` (fixed)

A `DD`/`FD` prefix is fetched as a separate M1 cycle that doesn't touch the flags, so Q is 0
afterwards. `DD 37` (SCF) must then take X/Y from `A | F`. **Fix:** the prefix cases shift
`FlagsChanged` once more before dispatching. This is on the prefix path only. The effect is
undocumented flags only.

### 8. `EX (SP),HL` write order (fixed)

Hardware (and the suite) write `(SP+1)` then `(SP)`. MesenCE wrote them in the other order.
Timing and results were already correct. Only the bus order changes, which matters for
write-triggered hardware such as mapper registers at `$FFFC-$FFFF` if the stack is there.

## 9. Coverage gap: no system-level SMS tests

MesenTests (what `mise run test:ci` runs) has GB, GBA, NES, PCE, SNES and WS tests, but none for
SMS/GG/Coleco. The fixes above were checked at instruction level, plus a full `test:ci` run for
the other systems, but not against any game or test ROM.

**Update: partly closed.** `tests/SMS/z80_timing.mtp` (source `tests/SMS/src/z80_timing.s`, run by
`test:ci`) is a self-checking ROM written for the fork. It times 14 instructions with the VDP V
counter: it syncs to the start of line 0, runs 456 unrolled copies (2 × 228 T-states per line),
and reads the V counter, so the line count is exactly 2T. It covers every instruction from fix 2,
the DDCB BIT alias from fix 3, and unchanged controls (NOP, `LD A,(HL)`, `RRD`, `BIT 0,(IX+d)`,
`EX (SP),HL/IX`).

- On the current core: all 14 match Zilog UM0080 ("ALL PASS").
- On a core with commit `7d48f58e` (fixes 2–8) reverted: "8 FAILED", and the measured values are
  exactly the "MesenCE before" column of fix 2's table, plus 19 for the DDCB alias. So the
  measurement through the whole system (CPU + VDP counters) agrees with the instruction-level
  result.

Still not covered at system level: WZ (4), block I/O flags (5), `LD A,I/R` (6), Q (7), the
`EX (SP),HL` write order (8), and anything involving interrupts. **Not yet run on hardware.**

## 10. Recorded SMS tests weren't reproducible (fixed, test mode only)

**Reproduction.** Recording `z80_timing` and replaying it with the CI runner's own function
(`RunRecordedTest`) gave "passed with warnings" with 1–3 mismatched frames, and two recordings
of the same ROM had different frame-hash sequences.

**Cause.** `SmsVdp::Init` starts the VDP on `RandomHelper::GetValue(0, 200)`, a random scanline
from `std::random_device`. Upstream did this on purpose so that Impossible Mission gets a random
stage ("TODOSMS"). It isn't gated by any setting (unlike the PCE's `EnableRandomPowerOnState`), so
every power-on, including the CI runner's replay, starts at a different point in the frame.

**Effect.** No SMS/GG test could ever replay exactly, so a timing change could only be caught
through the last frame. Movies recorded from power-on probably desync the same way. That hasn't
been checked, so it's not claimed here.

**Fix.** When `EmulationFlags::TestMode` is set (the CI runner and `tools/mtp-record` set it),
the VDP starts on scanline 0. Normal play keeps upstream's random start. **Judgment call:** this
follows the same idea as the recorder forcing all-zero RAM (`RecordedRomTest::UpdateSettings`).
After the fix, three recordings in a row gave identical frame hashes and every replay passed
exactly.

## Ideas for further SMS verification

- **Interrupts:** IM 1, IM 2, NMI, the EI delay, and `LD A,I` P/V when an interrupt is accepted
  (the suite's `p`/`ei`). These need a scenario harness like `tools/gb-irq-scenarios`. IM 0 is
  unimplemented (`TODOSMS`).
- The save-state round trip for `.sms`/`.gg`, which also needs SMS ROMs that can be distributed
  (e.g. homebrew test ROMs).
- Game Gear CMOS behaviour (`OUT (C),0`).
- More system-level tests in `tests/SMS`: interrupt timing (IM 1/NMI against the VDP), and
  hardware runs of `z80_timing.sms` (an SMS and a Game Gear).
- Whether SMS movies recorded from power-on desync because of the random VDP scanline (finding
  10), and whether movies/netplay should also start deterministically.
